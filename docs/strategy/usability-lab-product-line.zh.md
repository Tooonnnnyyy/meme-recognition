# Usability Lab 产品线方案（自问自答版）

> 状态：2026-11-15 草案。基于现有代码、两轮代码审查、平台调研和公开资料。
> 文中凡标 **[假设]** 的地方，都还没有用户证据，必须先访谈验证（见第 8 节）。

## 0. 一句话结论

- **不做"网页眼动工具"。** 单点功能很容易被取代，而且眼动的精度有限（约 3°）。
- **做一套给"受伦理约束的可用性测试"用的端到端工具链。** 目标用户是加拿大大学的 UX/HCI 学生和教师，以及对隐私敏感的小团队。
- **工具链覆盖八个环节：**计划 → 招募 → 执行 → 收数据 → 分析 → 报告 → 迭代 → 教学。
- **各环节之间：**共用一种开放的"研究包"数据格式，每个模块可以单独用，也可以无缝串起来。
- **和外部工具：**能接入研究员已经在用的 Figma、Framer、Webflow、Miro、Notion、Jira、Google Drive。
- **眼动和表情信号：**降为可选增强，不再当卖点。

## 1. 自问自答：逐层压测这个方向

**Q1. 用户到底是谁？**
- **初始用户：**加拿大大学里做可用性测试的学生和教师，例如 uOttawa MDTI、Carleton HCI。
  - 他们每学期都要做真实测试。
  - 研究要过伦理审查（TCPS 2）。
  - 几乎没有预算。
- **第二圈：**对数据驻留敏感的公共部门和小团队，比如政府数字服务、医疗、教育。
- **反问：**学生不付费，市场够大吗？
  - **回答：**这一阶段的成功标准不是收入，而是三件事：1–2 门课实际采用、做出真实研究、形成作品集。
  - 采用路径是自下而上：老师在课上推荐，学生就会用。

**Q2. 他们雇这个工具来完成什么任务？**
- 让一个可用性研究从计划走到报告，并且经得起老师、伦理委员会和利益相关方的追问。
- 拆成八个环节的工作，见第 3 节。

**Q3. 痛点有证据吗？**
- **有外部证据的：**
  - **时间和人手不够是行业第一痛点，招募排第二。**[Maze 2024 调研] 报告约 62% 和 60%；2025 年的数字还需要回原始报告核实。
  - **加拿大的伦理委员会普遍要求说明数据驻留，并优先使用加拿大境内或机构自有的工具。**
    - Zoom 云录像因为不在加拿大境内存储，被要求立即删除或说明如何降低风险 [U Regina 2026]。
    - 有学校要求研究员优先选用加拿大公司、服务器在加拿大的工具 [Lakehead]。
    - 有学校规定必须用学校账号的 Zoom，不能用个人账号 [U Manitoba]。
- **[假设]，需要访谈验证的：**
  - 学生做一次课程测试要拼 5 个以上的工具：Zoom 录像、Google Forms 收 SUS、表格算指标、Miro 做亲和图、Docs 写报告。工具割裂本身就是痛点。
  - 主流美国云端工具（Maze、Lookback、UserTesting）让伦理审批变复杂，或者免费档不够一门课用。

**Q4. 凭什么不用 Maze、Lyssna 加 Google Forms 加 Zoom？**
差异点按难以复制的程度排序：
1. **本地优先、可写进伦理申请：**数据只在参与者和研究员手里，可选端到端加密。工具自动生成伦理申请里需要的"数据流向说明"和知情同意书模板。云端商业模式很难照搬这一点。
2. **课程测试一站式：**一个工具走完计划、实验室或远程执行、标准问卷、带置信区间的统计和报告，全部免费。
3. **兼容任意原型，输出到研究员已有的工具：**
   - 原型来源：Figma、Framer、Webflow、Carrd、Axure、Bubble 和任意 HTML 导出。
   - 结果去向：Miro 和 FigJam 的便签、Notion 和 Docs 的报告、Jira 和 Linear 的问题清单、R 和 SPSS 用的 CSV。
4. **教学层：**指标旁边有通俗解释；有老师模板、助教批改视图和示例数据集。
- **反问：**Maze 会不会做本地版？短期内不太可能，因为它的商业模式依赖云端数据。

**Q5. 真能解决问题吗？准确性怎么保证？**详见第 5 节。核心原则有三条：
- 自动结果只当"候选"，必须由人确认。
- 每个数字都附上样本量和置信区间。
- 检测效果要用人工观察作为标准答案，量出准确率和召回率，没有量过就不对外宣称。

**Q6. 真的容易用吗？**现在不容易，见第 4 节的逐秒痛点。设定三条可以衡量的易用目标：
- 研究员从零到发出第一个研究：不超过 **10 分钟**，不写代码。
- 参与者进入第一个任务前的额外开销：不超过 **90 秒**（不开摄像头）。
- 从最后一位参与者做完到拿到可交的报告：不超过 **1 小时**。

**Q7. 做单一产品还是产品线？**产品线，参照 Google 网站工具家族的思路：
- Lighthouse、PageSpeed Insights、Search Console 共用同一套指标定义，各自可以单独使用，组合起来又互相增强。
- 对应到我们这里：共用的是"研究包"格式和指标定义；每个环节都是一个模块。

**Q8. 最小可证明价值的链路是什么？**
- 一门课的一次标准测试：5 名参与者、在实验室、测 Figma 或网站原型。
- 链路：模板 → 实验室模式执行，并记下观察员笔记 → 自动指标、候选问题和笔记汇总 → 导出报告到 Docs 或 Miro。
- **口号：一个下午，从空白到可以交作业的报告。**

**Q9. 什么情况下应该停下或转向？**
- 访谈显示学生很少找真人测试，或者现有工具完全够用 → 转成教学资源和作品集项目，停止扩功能。
- 没人在乎眼动 → 眼动功能彻底降为实验性。
- Figma 事件拿不到，比如不登录的参与者收不到 → Figma 改走"导出 HTML 加探针"的路线。

**Q10. 哪些明确不做？**
- 上传视频。
- 表情或情绪识别（不给情绪贴标签，这是伦理红线）。
- 招募付费参与者的市场。
- 需要我们自建后端的实时多人协作。

## 2. 360° 人群与未满足需求

| 人群 | 场景 | 未满足的需求或痛点 | 我们的解法 |
|---|---|---|---|
| 学生研究员（主要） | 课程测试、毕业项目 | 工具割裂；伦理文件难写；统计不会做；不知道怎么交接数据；时间紧 | 研究模板；伦理文件生成器；自动统计并附解释；实验室模式零交接；一键报告 |
| 老师 | 布置测试作业 | 每个学生用的工具都不一样，没法统一要求和批改 | 课程模板（统一任务和问卷）；助教只读视图；评分要点核对 |
| 助教或评审 | 批改作业 | 只看报告看不出过程是否规范 | 研究包里附上过程证据：同意记录、任务设置、原始指标 |
| 小团队、自由职业 UX 研究员 | 客户项目 | 云工具贵，客户数据不能外传 | 本地优先加端到端加密；白标报告 |
| 利益相关方（产品经理、客户、老师） | 读报告 | 看不懂置信区间，不知道该先修什么 | 一页摘要：先修哪 3 个问题、证据片段、看得懂的不确定性表述 |
| 参与者：普通成年人 | 远程或到场 | 怕摄像头；不知道要花多久；不知道结束后要做什么 | 开头写明时长；摄像头完全可选；结束后一键提交 |
| 参与者：老年人或数字新手 | 到场 | 校准太麻烦，字太小 | 实验室模式由主持人代为操作；大字号；跳过校准 |
| 参与者：读屏器或键盘用户 | 无障碍测试 | 校准点、评分控件不可达 | 全流程支持键盘和读屏；无障碍测试模板；不依赖眼动 |
| 参与者：只用手机 | 远程 | 布局问题；无法校准 | 手机流程自动关闭眼动；测试移动端原型 |
| 参与者：讲法语或非英语母语 | 加拿大双语环境 | 界面只有英文 | 英法双语界面（加拿大的硬需求） |
| 参与者：未成年人或弱势群体 | 特殊研究 | 需要监护人同意 | 同意书模板支持监护人签署；最少化采集 |

## 3. 产品线：八个模块，一种数据格式

共用的底座是**研究包**（Study Package）：一种开放、带版本号的 JSON 格式，装着研究定义、各场次数据、评审、笔记和报告设置。
- 每个模块读写同一种格式，可以离线、导入导出。
- 有一个"数据流向清单"自动生成器，直接写进伦理申请。

| 模块 | 做什么 | 现状 |
|---|---|---|
| ① 计划：研究构建器 | 目标 → 任务（含成功标准）→ 问卷 → 同意书；模板库（结账、注册、导航和信息架构、内容可找性、无障碍）；导出主持人手册 | 只有 Figma 能用界面设置，网站要改代码 → **补齐** |
| ② 招募和筛选 | 筛选问卷、参与者编号、任务顺序平衡（拉丁方）、A/B 版本分配、邀请文案和二维码 | 无 |
| ③ 执行：连接器 | 同源网站（已有）；Figma Embed（已有，待真机验证）；**探针一行代码**（Framer、Webflow、Carrd、Axure、Bubble；Wix、Squarespace、WP 需先测）；**HTML 导出包**（Webflow、Carrd、Axure、UXPin、Notion 导出）；无法接入的工具只记录计时、问卷和眼动 | 部分 |
| ③ 执行：模式 | **实验室模式**：主持场次、本机自动保存、观察员带时间戳的快捷笔记；远程无主持（已有）；远程有主持（之后用 WebRTC 点对点做） | 只有远程无主持 |
| ③ 执行：方法插件 | 任务式可用性测试（已有）；第一次点击测试；5 秒测试；偏好和 A/B 测试；树测试；卡片分类；纯问卷（SUS、UMUX-Lite、NASA-TLX、自定义） | 只有第一种 |
| ④ 收数据：交接 | 实验室模式自动保存；远程一键提交到研究员自己的 Google Drive 或 OneDrive，用模板脚本搭建；可选用研究员公钥加密，邮件发送也安全；下载作为兜底 | 只能手动下载 |
| ⑤ 分析 | 单场回看（已有）；观察笔记和标签做亲和图；点击图和第一次点击热力图；路径分析（预期路径和实际路径、迷失度）；候选时刻附近 20 秒的出声思考录音（本地）；多人严重度评分一致性 | 部分 |
| ⑥ 报告和分享 | 研究报告（已有）；利益相关方一页摘要（可打印或存 PDF）；问题导出到 Jira、Linear、GitHub；Markdown 导出到 Notion 和 Docs；便签导出到 Miro 和 FigJam；两轮或两个版本的统计对比 | 部分 |
| ⑦ 迭代 | 同一研究多轮对比，形成基准历史 | 无 |
| ⑧ 教学 | 指标解释；引导做第一次研究；老师模板；助教视图；示例数据 | 无 |

## 4. 逐秒痛点（基于当前版本，部分时长为估计）

**参与者**
| 时刻 | 痛点 | 改进 |
|---|---|---|
| 0–5 秒 打开链接 | 不知道要花多久、要做什么 | 首屏写明"约 10 分钟、3 个任务、摄像头可选" |
| 5–40 秒 读同意书 | 文字多，有两个勾选框 | 分层同意：先给摘要，展开看全文；仍然符合 TCPS 2 |
| 40–60 秒 摄像头授权 | 浏览器弹窗让人紧张；拒绝之后路径不清楚 | 授权前先解释为什么需要；把"不开摄像头继续"做成同样醒目的按钮 |
| 60–90 秒 加载模型 | 等待时没有进度 | 显示进度条；加载时可以先读第一个任务 |
| 1.5–3 分钟 校准 18 个点 | 太长，容易分心 | 快速 5 点校准加验证；不达标就自动关眼动，不让人重来 |
| 每个任务 | 嵌入窗口里迷路，不知道怎么回到起点 | 加"重新开始本任务"按钮；任务说明可以随时展开 |
| 每题 SEQ | 打断节奏 | 一次点击作答（已做） |
| 结尾 SUS | 10 题偏长 | 允许研究员换成 UMUX-Lite（2 题） |
| 结束 | **下载文件之后不知道要做什么**（最大断点） | 一键提交；实验室模式自动保存 |

**研究员**
| 环节 | 痛点 | 改进 |
|---|---|---|
| 搭建网站研究 | 要改代码 | 用界面搭建 |
| 搭建 Figma 研究 | 要去开发者后台注册 client ID，粘贴节点 ID | 系统内置 client ID（你注册一次即可）；用画框选择器选起点和目标 |
| 先自己试跑 | 没有"试跑"标记，试跑数据会混进正式数据 | 加试跑模式 |
| 发放 | 只能发链接；不知道谁做完了 | 二维码；提交后自动登记"已完成" |
| 收数据 | 文件散在邮件附件里，文件名混乱 | 一键提交到研究员的 Drive，自动命名 |
| 回看 | 一个文件一个文件地打开 | 研究工作区：所有场次一览，逐个过 |
| 报告 | 有统计错误（见第 7 节）；没有"先修哪个"的建议 | 修好统计错误；报告按优先级给出前 3 个问题 |

## 5. 准确性保证体系

| 层 | 方法 | 现状 |
|---|---|---|
| 统计公式 | 与独立实现交叉验证：adjusted Wald、t 分布、几何均值、SUS、等级曲线 | **已验证**：随机样本上的最大误差小于 1e-3 |
| 任务完成判定 | 到达目标页或目标画框，属于确定性判定；Figma 收不到事件时标为"不可验证"，不算失败 | 待修 |
| 候选时刻检测 | 建立一个标准答案数据集：脚本模拟的已知问题，作为回归测试；再做 5–8 人试点，由 2 名观察员独立标注，计算准确率和召回率。目标是强信号召回率 ≥ 0.8、准确率 ≥ 0.6 | 只有合成测试，**缺真人数据** |
| 眼动 | 每人做验证，误差超过 3° 就关闭；只给区域级的结论 | 已有 |
| 人工评审一致性 | 两人独立打严重度，算 Cohen's κ 或 ICC，κ < 0.6 就讨论校准 | 无 |
| 透明度 | 每个数字附 n 和置信区间；系统失灵时明示（收不到 Figma 事件、相机中断） | 部分 |
| 过程证据 | 研究包里记录版本、设置和同意时间，供老师或伦理委员会抽查 | 部分 |

## 6. 路线图（每个版本都能单独上线）

| 版本 | 目标 | 内容 |
|---|---|---|
| R1 能交课程作业（2–3 周） | 一个下午出报告 | 报告统计修复；实验室模式（本机工作区、观察员笔记）；网站研究用界面搭建；同意书和伦理文件生成器；试跑模式 |
| R2 连接一切 | 任意原型、远程零交接 | 探针加各平台粘贴指南；HTML 导出包；一键提交到研究员的 Drive 加可选加密；Figma 画框选择器；任务顺序平衡 |
| R3 方法齐全 | 覆盖常见方法 | 第一次点击测试；5 秒测试；偏好和 A/B 测试；问卷库；本地出声思考录音 |
| R4 分析和分享 | 从"有数据"到"有结论" | 亲和图；点击图和路径分析；多轮对比统计；导出到 Miro、Notion、Jira；利益相关方一页摘要；评分一致性 |
| R5 教学 | 课程级采用 | 老师模板；助教视图；示例数据；英法双语 |

## 7. 已发现、待修复的问题（统计审查，已附复现脚本）

**高：**Figma 里不同位置的无响应点击被合并成同一个问题。

**中：**
- 先载入原始文件、再载入审阅过的文件，审阅结果被丢弃。
- 一个时刻里只统计第一个信号，所以问题频次偏低。
- 被否决的时刻仍然计入受影响人数。
- Figma 收不到事件时，完成率显示为 0%。
- 同一个 Figma 文件做的不同研究共用一个研究 ID。
- Figma 任务的计时包含了原型加载时间。

**低：**
- 排序规则不合理。
- 时间显示出现"1 min 60 s"。
- Markdown 表格遇到换行会断开。
- CSV 各行列数不齐。
- t 分布表只到 30 个自由度。
- 所有值相同时置信区间宽度为 0。

## 8. 两周验证计划（与 R1 并行）

1. **访谈 8 人：**4 名学生、2 名老师或助教、2 名在职研究员。
   - 只问"上一次做可用性测试"的真实经历：用了哪些工具、每一步花了多久、伦理审查卡在哪、数据怎么收、报告给谁看。
   - 逐条验证 Q3 里的假设。
2. **真实试点：**用 R1 的实验室模式给 5 名同学测一个真实网站。
   - 量出：从准备到出报告的总时长、参与者的额外开销秒数、候选时刻的准确率和召回率，以及参与者给我们这个工具本身打的 SUS 分。
3. **决策会：**按第 1 节 Q9 的停止或转向条件决定下一步。
